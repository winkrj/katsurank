# 카츠랭 백엔드 성능 실험 이력

이 문서는 `backend/loadtest` 실험의 목적, 완료 상태, 현재 코드에 대한 유효성을 구분하는 색인이다.
성능 수치는 실행 당시 환경과 코드에만 유효하며, 원본 결과를 덮어쓰지 않는다.

이 문서는 AI 분석·검산·재현을 위한 기술 자료다. 처음 읽는 사람을 위한 문제 해결 이야기는
[PERFORMANCE_STORY.md](PERFORMANCE_STORY.md)에서 먼저 확인한다.

## 변화의 흐름

1. EXP-01에서 CPU, DB pool, GC, 부하 발생기와 관측 도구 자체의 비용을 분리했다.
2. EXP-02에서 2초·1초 polling이 Hikari 대기와 지연을 크게 만드는 것을 확인했다.
3. EXP-02B에서 시작 지터가 일부 실행을 개선했지만 포화를 근본적으로 제거하지 못함을 확인했다.
4. EXP-03에서 TOP 20 캐시의 응답 개선을 확인했다.
5. EXP-04에서 REST polling의 실현 처리량 한계를 관측했다.
6. PR #34에서 polling REST 계약은 유지하면서 단일 인스턴스 캐시와 SSE 알림을 추가했다.
7. EXP-05·06으로 연결 비용, 투표 전파, 캐시 주기를 측정했다.

## 현재 결과를 인용할 때의 제한

### EXP-02~04

- 제품 런타임이 의존하는 파일이 아니라 캐시·SSE 도입 근거다.
- 일부 분석은 로컬 Prometheus 데이터에 의존하므로 저장된 CSV만으로 완전 재생되지 않는다.
- EXP-03은 캐시 hit 요청에도 트랜잭션이 열리던 시점의 결과다. 현재의
  `RankingPageQueryService` 분리 이후 성능을 대표하지 않는다.
- EXP-04 v2는 완료되지 않았으며 최종 수치로 인용하지 않는다.

### EXP-05·06

- `results/**/final-v3`는 2026-08-17 측정이다.
- 당시 SSE 이벤트 이름은 `ranking-snapshot`이었고 현재 계약은 `vote-changed`다.
- 2026-08-29~30에 클라이언트, 수집기, 분석기의 오류 처리를 보강했다.
- 따라서 기존 raw 결과는 당시 실행 증거로 보존하되, 현재 V1 출시 근거는 최신 코드로 3회 재측정한다.

## 재실행 원칙

- 기존 `results` 디렉터리를 덮어쓰지 않고 새 실행 디렉터리를 사용한다.
- 실행 코드 commit, 애플리케이션 commit, 환경 설정, 시작·종료 시각을 함께 기록한다.
- 결측치는 0으로 대체하지 않는다.
- 목표 RPS와 실제 RPS를 분리해 보고한다.
- histogram 백분위는 누적 bucket delta를 사용하고 bucket 내부를 보간한다.
- 실행 후 analyzer의 유효성 검사와 원본 CSV 열 수 검사를 모두 통과해야 완료로 본다.
