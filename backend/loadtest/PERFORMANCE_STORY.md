# 카츠랭 랭킹 백엔드는 왜 캐시와 SSE를 함께 준비했나

> 한 줄 요약: 모두가 같은 랭킹을 반복해서 받아 가는 구조에서 DB 대기열이 병목이 됐고,
> 캐시만 붙이는 데서 멈추지 않고 **캐시 조회 경로 분리 + TOP 20 스냅샷 SSE**까지 단계적으로 개선했다.

이 문서는 사람을 위한 설명이다. 실험을 그대로 재현하거나 세부 수치를 검산하려면
[EXPERIMENT_HISTORY.md](EXPERIMENT_HISTORY.md)와 각 분석기·원본 결과를 사용한다.

## 먼저 보는 전체 흐름

| 순서 | 당시 질문 | 확인한 사실 | 다음 선택 |
|---:|---|---|---|
| 1 | 느려지는 원인이 정말 DB인가? | CPU, DB 연결 대기, GC, 부하 발생기를 따로 볼 수 있는 환경을 만들었다. | 추측 대신 같은 지표로 비교한다. |
| 2 | 사용자가 자주 새로고침하면 어떻게 되는가? | 1~2초 polling에서 DB 연결 대기열과 응답 시간이 급증했다. | 요청 시작 시각을 흩어 본다. |
| 3 | 요청 시각만 흩으면 해결되는가? | 평균은 좋아졌지만 실행마다 다시 포화될 수 있었다. | 같은 랭킹을 매번 DB에서 읽지 않는다. |
| 4 | TOP 20을 캐시하면 충분한가? | 캐시는 잘 맞았지만 기존 트랜잭션 경계 때문에 DB 연결 비용이 남았다. | 캐시 hit 경로를 트랜잭션 밖으로 분리한다. |
| 5 | 서버가 감당할 수 있는 경계는 어디인가? | REST polling은 약 2천 RPS 부근부터 대기와 지연이 가파르게 늘었다. | 변경이 있을 때만 알리는 구조를 검토한다. |
| 6 | REST를 깨지 않고 실시간 경로를 추가할 수 있는가? | 기존 REST는 유지하고, 투표 후 TOP 20을 담은 `vote-changed` SSE를 보내는 백엔드 경로를 추가했다. | 연결 비용과 전파 지연을 검증한다. |

```text
반복 polling
    ↓
DB 연결 대기 증가
    ↓
지터 실험 ── 평균은 개선, 근본 해결은 아님
    ↓
TOP 20 캐시 ── 같은 조회 반복은 감소, 트랜잭션 비용 발견
    ↓
캐시 조회 경로 분리 + TOP 20 스냅샷 SSE
    ↓
polling을 대체할 수 있는 백엔드 실시간 경로 확보
```

## 1. 처음에는 “느리다”가 아니라 “왜 느린가”부터 확인했다

부하 테스트 숫자 하나만 보면 원인을 잘못 짚기 쉽다. 애플리케이션이 느린 것인지,
DB 연결을 기다리는 것인지, GC가 멈춘 것인지, 테스트를 만드는 k6가 한계인지 구분할 필요가 있었다.

그래서 먼저 다음을 같은 시간축에 놓았다.

- 실제 요청 수와 응답 시간
- DB 연결 사용 수와 대기 수
- 애플리케이션·시스템·k6 CPU
- heap, GC pause, 파일 디스크립터
- 목표 RPS와 실제로 만들어진 RPS

이렇게 원인을 분리해 볼 수 있는 관측 환경을 만든 것이 이후 모든 실험의 기준점이 됐다.
이 단계가 기술 실험의 EXP-01이다.

## 2. 자주 확인할수록 최신이 되지만, 서버는 더 느려졌다

1,000명이 랭킹을 보고 있다고 가정하고 polling 간격을 바꿨다.

| polling 간격 | 실제 처리량 | 응답 시간 p95 | DB 연결 대기 최대 |
|---:|---:|---:|---:|
| 30초 | 약 29 RPS | 첫 실행 약 22ms | 0 |
| 2초 | 약 375 RPS | 약 2.56초 | 951 |
| 1초 | 약 357 RPS | 약 3.98초 | 981 |

_출처 조건: EXP-02, 2026-08-09, 로컬 단일 인스턴스, 각 핵심 조건 1회._

간격을 절반으로 줄였는데 처리량은 늘지 않고 오히려 응답만 더 늦어졌다. DB pool의 활성 연결은
10개로 꽉 찼고, 거의 1,000개의 요청이 연결을 기다렸다. 병목은 단순한 SQL 실행 시간보다
**모든 사용자가 같은 시각에 같은 랭킹을 다시 요청하는 구조**에 가까웠다.

이 수치는 당시 로컬 환경의 결과이므로 서비스 용량 보증값은 아니다. 여기서 중요한 것은 절대 숫자가
아니라 polling 빈도를 높일수록 대기열이 급격히 커졌다는 방향성이다.

## 3. 요청 시작 시각을 흩어도 근본 원인은 남았다

모든 가상 사용자가 동시에 요청하지 않도록 시작 시각에 지터를 넣었다. 세 번의 정식 실행 중 두 번은
응답 p95가 약 92~108ms까지 좋아졌지만, 한 번은 다시 약 2.51초로 악화됐다.

_출처 조건: EXP-02B, 2026-08-09, 로컬 단일 인스턴스, 정식 실행 3회._

이 결과는 지터가 쓸모없다는 뜻이 아니다. 순간적인 쏠림을 완화하는 안전장치로는 효과가 있지만,
사용자 수에 비례해 동일한 REST 요청이 계속 발생한다는 구조 자체는 바꾸지 못한다는 뜻이다.

## 4. 캐시는 맞았지만, 캐시만으로 끝내지 않았다

서울 전체 TOP 20은 모든 사용자에게 같은 데이터다. 그래서 1초 동안 결과를 재사용하는 캐시를 시험했다.
다섯 번의 실험에서 측정된 요청은 모두 캐시에 적중했고, 캐시 갱신 실패도 없었다.

_출처 조건: EXP-03, 로컬 단일 인스턴스, 반복 실행 5회. 최신 트랜잭션 구조 이전 결과._

하지만 예상 밖의 사실도 발견했다. 당시 구조에서는 캐시가 맞아도 서비스 메서드에 걸린 읽기 트랜잭션이
먼저 시작되어, 요청당 DB 연결 획득이 거의 한 번씩 남아 있었다. “캐시 적중률 100%”만 보고 성공이라고
결론 냈다면 놓쳤을 문제다.

최신 구현에서는 이를 다음처럼 분리했다.

- 캐시 hit: 트랜잭션 없이 즉시 반환
- 캐시 miss와 실제 조회: 별도 조회 서비스의 읽기 트랜잭션에서 처리
- 기존 REST 응답 DTO와 URL: 그대로 유지

## 5. 서버의 무릎 지점을 찾아 무리한 목표를 버렸다

REST polling 부하를 500 → 1,000 → 2,000 → 5,000 → 10,000 목표 RPS로 올렸다.
세 번의 실행에서 약 2,000 목표 구간까지는 실제 약 1,843~1,878 RPS를 처리했지만,
5,000을 목표로 해도 실제 처리량은 약 2,179~2,305 RPS 부근에서 더 늘지 않았다.

_출처 조건: EXP-04, 로컬 단일 인스턴스, 반복 실행 3회. 목표가 아닌 실제 RPS 기준._

그 구간부터 CPU가 거의 100%에 도달하고 DB 연결 대기와 p95 지연이 함께 급증했다. 이것은
“서버가 초당 정확히 2,000건까지 보장한다”는 결론이 아니라, 현재 로컬 조건에서 구조가 꺾이는 위치를
찾아낸 것이다. 부하 발생기가 목표를 전부 만들지 못한 구간도 있어 목표 RPS와 실제 RPS를 구분했다.

## 6. 백엔드 선택: 변경된 TOP 20을 SSE로 전송한다

기존 REST 랭킹 API를 없애거나 응답 형식을 바꾸지 않았다. 백엔드 SSE는 이벤트 이름만 보내는
signal-only 방식이 아니라, `version`, 변경·생성 시각과 서울 TOP 20 전체를 담은
`RankingSnapshotEvent`를 전송한다. 클라이언트는 이 스냅샷을 직접 반영할 수 있고, 필요하면 기존 REST를
다시 조회할 수도 있다.

이번 작업 범위에서는 프론트엔드를 확인하지 않았으므로 실제 화면이 polling을 중단하고 SSE를 소비하는지는
검증하지 않았다. 완료된 것은 **polling을 대체할 수 있는 백엔드 실시간 경로**까지다.

```text
투표 또는 표 이동 성공
        ↓
DB 트랜잭션 커밋
        ↓
변경 마커 기록
        ↓
다음 캐시 갱신에서 TOP 20 생성
        ↓
vote-changed 이벤트 전파
        ↓
TOP 20 스냅샷 수신
```

여기서 “커밋 후”는 순서를 보장한다는 뜻이지 즉시 전송을 보장한다는 뜻은 아니다. 기본 설정에서는
다음 캐시 갱신까지 최대 약 1초를 기다릴 수 있다. EXP-05·06은 이 캐시 대기와 실제 SSE 전송 시간을
나눠 측정하려던 실험이다.

이 순서에는 몇 가지 의도가 있다.

- 롤백된 투표가 알림으로 먼저 나가지 않게 커밋 이후 전파한다.
- TOP 20 밖의 투표도 순위 진입 가능성이 있으므로 빠뜨리지 않는다.
- 느린 클라이언트 하나가 다른 연결을 막지 않도록 연결별로 전송한다.
- 같은 클라이언트에 스냅샷이 몰리면 최신 version만 남겨 중복 전송을 줄인다.
- 연결 수 상한을 넘으면 503으로 명확하게 거부한다.

## 현재 어디까지 믿을 수 있나

| 표시 | 의미 |
|---|---|
| **역사적 근거** | 로컬 원본과 당시 분석 결과가 보존돼 있다. 일부는 Prometheus 없이 완전 재계산할 수 없다. |
| **코드 검증됨** | 최신 동작을 단위·통합 테스트로 확인했다. |
| **재측정 필요** | 과거 결과는 있지만 최신 SSE 계약의 최종 성능 수치로 인용하면 안 된다. |

- **역사적 근거:** polling 간격, 지터, 캐시, REST 처리량 경계를 탐색한 과정
- **코드 검증됨:** 커밋 후 신호, TOP 20 밖 투표, `vote-changed`, 느린 연결 격리, 연결 상한
- **재측정 필요:** 최신 코드의 1,000 SSE 연결 비용과 캐시 주기별 전파 지연
- **완료되지 않음:** EXP-04 v2. 중단된 실행으로 보존하며 결과 수치로 사용하지 않는다.

## GitHub에서 이 폴더를 읽는 순서

1. 이 문서에서 문제와 의사결정 흐름을 읽는다.
2. [EXPERIMENT_HISTORY.md](EXPERIMENT_HISTORY.md)에서 실험별 완료 상태와 인용 제한을 확인한다.
3. [README.md](README.md)에서 실행 환경과 재현 방법을 확인한다.
4. `results/`는 Git에서 제외되므로 GitHub에서는 보이지 않는다. 로컬 원본을 가진 검증자만 연다.
5. `analyze_exp*.py`는 원본에서 요약 수치를 다시 만들 때 사용한다.

GitHub에 공개되는 요약 근거는 이 문서와 기술 이력이다. 전체 raw 결과는 크기와 실행 환경 정보를
포함하므로 로컬에 보존하고, 공개 문서의 수치를 운영 용량 보증값으로 사용하지 않는다.

## 블로그 글로 옮길 때의 뼈대

추천 제목:

> 캐시 적중률 100%인데 왜 DB 연결을 쓸까: 랭킹 polling을 줄이기 위한 백엔드 실험

글의 순서:

1. 서비스 특성: 서울 전체가 같은 TOP 20을 본다.
2. 문제 장면: polling을 1초로 줄이자 DB 연결 대기가 981까지 늘었다.
3. 첫 시도: 지터로 쏠림을 완화했지만 실행마다 결과가 흔들렸다.
4. 두 번째 시도: 캐시 적중률은 100%였지만 트랜잭션 때문에 연결 획득이 남았다.
5. 구조 개선: 캐시 hit 경로를 분리하고, 커밋 후 다음 캐시 갱신에서 TOP 20을 `vote-changed`로 보냈다.
6. 안전장치: 느린 연결 격리, 최신 스냅샷 병합, 연결 상한과 503.
7. 정직한 결론: 백엔드 계약은 검증했지만 프론트 연동과 최신 성능 수치는 확인 전이다.

이 이야기를 쓸 때 EXP 번호는 각주나 재현 링크로만 사용한다. 본문에서는 “polling 간격 실험”,
“지터 실험”, “캐시 검증”처럼 목적을 먼저 말하면 독자가 중간부터 읽어도 이해할 수 있다.

## 용어를 짧게 풀면

- **polling:** 브라우저가 일정 시간마다 서버에 “바뀌었나요?”라고 묻는 방식
- **SSE:** 서버가 연결을 유지하다가 변경된 TOP 20을 브라우저에 보내는 방식
- **p95:** 요청 100개 중 느린 쪽 다섯 번째 정도의 응답 시간
- **DB pool:** 여러 요청이 나눠 쓰는 제한된 DB 연결 묶음
- **지터:** 요청이 한순간에 몰리지 않도록 시작 시각을 조금씩 흩는 것
- **RPS:** 서버가 1초에 실제로 처리한 요청 수
