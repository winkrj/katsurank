# 카츠랭 기술적 의사결정

이 문서는 포트폴리오 독자가 “무엇을 사용했는가”보다 “왜 그렇게 선택했는가”를 빠르게 확인하기 위한
요약이다. 상세 구현과 과거 실험은 연결된 코드·문서를 따른다.

## 1. 서울 전체 랭킹 하나만 유지한다

- 대안: 지도 bounds에 따라 매번 달라지는 지역 랭킹
- 선택: 지도는 탐색, 랭킹은 서울 전체 단 하나로 역할 분리
- 이유: “서울 1위라는 왕좌”가 서비스의 핵심 메시지이기 때문이다.
- 감수한 비용: 가까운 가게를 찾는 편의보다 단일 경쟁의 명확성을 우선했다.
- 재검토: 가게가 수백 곳으로 늘어 탐색 불편이 반복되면 지역 필터를 보조 기능으로 검토한다.

## 2. 1인 1표는 DB와 애플리케이션이 함께 지킨다

- 부분 유니크 인덱스가 사용자별 현재 유효표 한 장을 최종 보장한다.
- `Restaurant.vote_count`는 낙관적 락으로 lost update를 막는다.
- 경합은 `TransactionTemplate`로 새 트랜잭션을 만들어 제한 재시도한다.
- 기존 표를 먼저 비활성화하고 flush해 같은 트랜잭션의 유니크 충돌을 피한다.
- 같은 가게 재투표는 멱등 응답으로 처리한다.

단순한 `exists` 검사만으로는 동시 요청 사이의 경쟁 조건을 막을 수 없다고 판단했다.

## 3. JWT가 아니라 외부저장소 세션을 사용한다

- 대안: JWT 기반 무상태 인증
- 선택: 카카오 OAuth2 + `spring-session-jdbc`
- 이유: 로그아웃과 세션 종료를 서버가 통제하고, 향후 계정 단위 강제 무효화로 확장할 기반을 둔다.
- 보안: HttpOnly 세션 쿠키, SameSite 정책, 허용 origin CORS, Double Submit Cookie CSRF
- 감수한 비용: 요청마다 세션 저장소 접근이 생긴다.
- 재검토: 네이티브 앱 또는 다중 서비스가 생기거나 세션 DB 비용이 실제 병목이 될 때 검토한다.

현재 구현된 것은 사용자 로그아웃과 해당 세션 종료다. 운영자 계정 차단이나 한 사용자의 모든 세션을
즉시 끝내는 관리 기능까지 구현됐다는 뜻은 아니다.

## 4. 삭제보다 상태와 히스토리를 선택한다

- 폐업은 `CLOSED`로 박제하고 기존 표를 보존한다.
- 이전은 `RELOCATED`와 `relocated_to_id`로 연결하고 현재 표를 새 가게로 승계한다.
- 표 이동도 기존 Vote를 삭제하지 않고 `is_current=false`로 남긴다.

제품의 “표는 누군가의 진심”이라는 규칙을 데이터 보존 정책까지 이어 갔다. 대신 모든 랭킹·투표
경로에서 ACTIVE 상태를 명시해야 하는 복잡성을 감수했다.

## 5. JPA와 QueryDSL의 역할을 나눈다

- 엔티티 저장과 단순 조회: Spring Data JPA
- 랭킹·검색·마이페이지처럼 projection과 동적 조건이 필요한 조회: QueryDSL
- 엔티티를 API 응답으로 직접 노출하지 않고 record DTO로 변환

풀 헥사고날 아키텍처 대신 기능별 패키지 안의 Controller → Service → Repository 3계층을 유지한다.
현재 팀과 서비스 규모에서는 인터페이스 계층을 추가하는 비용이 교체 가능성보다 크다고 판단했다.

## 6. polling 병목은 지터 하나로 덮지 않는다

실험 순서는 다음과 같았다.

1. CPU·DB pool·GC·부하 발생기를 함께 볼 수 있는 관측 환경 구축
2. polling 간격별 DB 연결 대기와 p95 비교
3. 지터로 동시 시작 완화
4. TOP 20 메모리 캐시 적용
5. REST 처리량의 무릎 지점 탐색
6. 캐시 조회 경로의 트랜잭션 제거와 SSE 스냅샷 전파

캐시 적중률만 보지 않고 캐시 hit 요청이 DB 연결을 계속 획득하는지도 측정했다. 최신 구조에서는
캐시 miss의 실제 조회만 `RankingPageQueryService` 트랜잭션에서 처리한다.

상세 과정: [성능 개선 이야기](../backend/loadtest/PERFORMANCE_STORY.md)

## 7. SSE는 signal-only가 아니라 versioned TOP 20 스냅샷이다

- 투표 성공 후 커밋된 변경 마커를 기록한다.
- 다음 캐시 갱신에서 TOP 20 스냅샷을 만들고 `vote-changed`로 전송한다.
- payload에 version과 변경·생성 시각을 넣어 최신성 판단이 가능하다.
- 느린 연결은 클라이언트별 비동기 전송으로 격리한다.
- 전송이 밀리면 가장 최신 version만 남겨 중복 스냅샷을 줄인다.
- 연결 상한을 넘으면 503으로 거부한다.

기존 REST API는 유지한다. 단일 인스턴스 V1에서는 인메모리 연결 관리가 충분하며, 서버가 여러 대로
늘어날 때 Redis Pub/Sub 같은 인스턴스 간 이벤트 전달을 검토한다.

현재 프론트 데스크톱 목록은 REST로 TOP 100까지 표시할 수 있어 TOP 20 snapshot으로 cache 전체를
교체하면 목록이 축소된다. 이벤트 이름뿐 아니라 이 결과 범위 정책도 통합 전에 확정해야 한다.

## 8. 기능은 얇게, 관측은 원인을 찾을 만큼 둔다

- traceId와 구조화 로그
- Actuator·Micrometer·Prometheus
- Hikari pool, heap, GC, 파일 디스크립터, 앱과 k6 CPU 분리
- k6 raw 결과와 분석기 유효성 검사
- 목표 RPS와 실제 RPS 분리, 결측치를 0으로 대체하지 않는 원칙

단일 성능 숫자를 홍보하기보다 측정 환경과 무효 조건을 함께 남기는 것을 우선한다.
