0.이 문서 사용법

이 문서는 docs/01~04에 줄글로 흩어져 있던 기획 내용을 한 화면에서 훑어보고 바로 의견을 남길 수 있게 재구성한 초안입니다. 완성본이 아니라 대화의 시작점입니다. 빨간 점선 박스([논의 필요])가 있는 부분은 아직 결정이 안 됐거나, 프론트/디자인 관점에서 이견이 있을 만한 지점입니다. 같이 보면서 의견을 정하고, 합의된 내용은 다시 docs/01~03 원본 문서와 옵시디언 노트에 반영합니다.

1.프로젝트 개요

누구를 위한, 무엇을 위한 서비스인가

서울에서 진짜 최고의 돈까스집 단 하나를 가리는 사이트. 카카오 로그인 사용자가 평생 단 한 집에만 투표하고, 더 맛있는 곳을 발견하면 표를 옮길 수 있습니다. 랭킹은 서울 단일 랭킹 하나뿐이며, 1위가 "왕좌"입니다.

타겟 사용자

서울에서 돈까스 맛집을 찾는 20~30대. 별점·리뷰 정보가 너무 많아 피로한 사람들.

핵심 컨셉

표 = 누군가의 1순위라는 진심. 별점 100개보다 무겁게 만든다.

규모/일정

1인 개발, 한 달 목표(하루 1~2시간). 수익 모델 없음(개인 프로젝트).

2.핵심 가치 & 차별점

기존 지도·리뷰 서비스와 뭐가 다른가

단순함

별점 0.5단위 고민 없음. 표 한 장이 전부.

신뢰감

표 = 한 사람의 1순위. 별점 100개보다 무거움.

단 하나의 왕좌

서울 1위 돈까스 단 한 집을 두고 모두가 경쟁.

공간감

지도로 후보를 탐색. 랭킹은 서울 전체 단일.

기존 서비스 (네이버지도·카카오맵·망고플레이트)카츠랭
평가 단위별점 (다회 가능)1인 1표 (평생)
신호 강도약함 (만족도)강함 (1순위)
카테고리전체 음식점돈까스 전용
핵심 화면검색·리뷰지도(탐색) + 서울 단일 랭킹
랭킹 단위지역·카테고리별 다수서울 1개 (단 하나의 1위)

3.비즈니스 로직 (정책)

화면을 만들기 전에 프론트가 알아야 하는 규칙들

투표 정책 확정

  • 카카오 로그인 필수, 1인 1표
  • 표 이동 가능 — 새 가게에 투표하면 이전 가게 표는 -1, 새 가게 +1
  • 표 이동 히스토리를 마이페이지에 시간순으로 표시
  • 동시성: 여러 사람이 동시에 투표해도 카운트가 안 깨지도록 서버에서 처리 (낙관적 락)

가게 데이터 정책 확정

  • 초기 20곳은 운영자가 수동 등록, 이후 사용자가 카카오맵 검색으로 추가
  • 카테고리 화이트리스트: "돈까스·돈가스·경양식" 키워드가 있어야 등록 가능 (검증 통과 시 즉시 ACTIVE)
  • 체인점 = 지점마다 별개 가게. 본점·분점을 합치지 않음 (지점마다 맛이 다르다고 보기 때문)
  • 하드 삭제 없음. 가게는 절대 안 지우고 상태로만 관리 (ACTIVE / CLOSED / RELOCATED / PENDING / REJECTED)

폐업 · 이전 정책 확정

  • 폐업 = 박제. 투표는 막지만 기존 표·히스토리는 보존, 랭킹에서만 제외. 마이페이지엔 "폐업한 ○○"로 표시
  • 이전 = 승계. 같은 가게가 자리만 옮긴 것이므로 표를 새 레코드로 이관
  • 감지는 MVP에서는 운영자 수동 (자동 감지·사용자 신고는 이후 버전)
[논의 필요] "폐업한 ○○"처럼 죽은 가게가 화면에 어떻게 보여야 자연스러울지 — 리스트에서 흐리게? 별도 섹션? UI 톤 상의 필요.

랭킹 로직 확정

  • 랭킹은 서울 전체 단일 랭킹 하나뿐. 지도를 확대/축소해도 랭킹은 안 바뀜
  • 정렬 기준: 표 수(vote_count) 내림차순, ACTIVE 상태만 포함
  • 30초 폴링으로 자동 갱신 (실시간 WebSocket 아님, 백그라운드 탭은 폴링 중지)

인증 방식 확정

  • 카카오 OAuth2 로그인만 지원. 이메일 없이 닉네임·프로필 이미지만 수집
  • JWT 대신 서버 세션 쿠키 사용 (어뷰징 계정을 즉시 차단하기 위함)
  • 프론트는 API 요청 시 쿠키를 항상 동봉(credentials: 'include'), CSRF 토큰 처리 필요

4.주요 플로우

사용자 행동 → 데이터 변화 → 화면 반영까지 흐름
4.1 로그인
1로그인 버튼 클릭프론트 어느 화면에서든
→
2카카오 인증 페이지window.location 이동
→
3로그인 + 동의카카오 쪽에서 처리
→
4백엔드 콜백User upsert, 세션쿠키 발급
→
5프론트로 리다이렉트로그인 완료 상태
4.2 투표 / 표 이동
1가게 상세 페이지투표하기 버튼
→
2로그인 여부 확인비로그인 시 로그인 유도
→
3기존 표 있는지 확인없으면 신규, 있으면 이동
→
4표 반영 (트랜잭션)이전 -1 / 신규 +1
→
5랭킹·마이페이지 갱신다음 폴링에 반영
4.3 가게 추가
1카카오맵 검색가게 추가 화면
→
2검색 결과 선택place_id 확보
→
3중복·카테고리 검증돈까스/돈가스/경양식만 통과
→
4a통과 → 즉시 ACTIVE바로 랭킹에 노출
4b실패 → REJECTED사유 안내 후 종료
[논의 필요] REJECTED 됐을 때 사용자에게 어떤 화면/문구를 보여줄지 아직 안 정해짐.
4.4 폐업 / 이전 처리 (운영자)
1폐업/이전 감지MVP는 운영자 수동 확인
→
2a폐업 → CLOSED투표 막힘, 표·히스토리 보존, 랭킹 제외
2b이전 → RELOCATED새 레코드 생성, relocated_to_id로 표 승계

6.아직 안 정해진 것 — 같이 정해야 할 것들

여기가 이 문서의 핵심 목적입니다. 이견이 있으면 바로 적어주세요.
  • API 응답 포맷 — 공통 ApiResponse 래퍼로 감쌀지, 순수 데이터 + HTTP 상태코드로 갈지 프론트 개발 시작 전 결정 필요
  • 프론트 최종 배포 위치 — Vercel이 유력하지만 확정 아님 M4 시작 전 결정
  • 개인정보처리방침 페이지 — 카카오 로그인 심사에 필수, 내용/디자인 담당 미정 출시 전 필수
  • REJECTED(카테고리 검증 실패) 시 사용자 경험 — 문구, 재시도 유도 방식 가게 추가 화면 설계 시 결정
  • 폐업한 가게의 리스트/지도 표현 방식 — 완전히 숨길지, 흐리게 남길지 디자인 톤 관련, 프론트와 상의 필요
